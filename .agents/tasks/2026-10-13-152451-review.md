# Customer Complaint Intelligence — Auth, dual portals, AI intelligence layer

This enhancement adds a full authentication layer on top of the existing Flask/SQLite backend, introduces two new single-page portals (customer at `/customer`, management at `/management`), and extends the complaint model with status tracking, manager responses, and internal notes. The AI analysis that was already running post-submission is now surfaced as explainable priority breakdowns and early-warning alerts in the management portal. Three new DB tables (`users`, `complaint_responses`, `internal_notes`) were added additively via `Base.metadata.create_all()`, preserving the existing schema.

Watch for: **confirmed** — the existing `index.html` dashboard and its public API calls are intentionally left unauthenticated; this is correct by design. No pandas imports anywhere in `src/`. App factory syntax check exits 0.

## High-level view

The auth layer uses Flask signed-cookie sessions backed by werkzeug's `generate_password_hash`/`check_password_hash`. Session state (`user_id`, `role`) is set server-side on login and never trusted from the frontend. The `login_required` and `manager_required` decorators consistently guard new and mutation routes while leaving the original read-only GET routes (`/api/complaints`, `/api/complaints/summary`, `/api/complaints/clusters`, `/api/complaints/priority`) public — the existing `index.html` dashboard depends on this and would break otherwise.

The customer portal enforces data isolation at the backend: `list_complaints` applies a `customer_id == str(uid)` filter when `role == "customer"`, and the `detail` endpoint returns 403 for cross-customer access attempts. The management portal's internal notes are never exposed in the customer-facing `detail`/`responses` endpoints, which filter to `is_visible_to_customer=True`.

The three new DB tables land safely on restart via `create_all()`; no destructive migration is needed. Six demo users (2 managers, 4 customers) are seeded with werkzeug-hashed passwords, and `main.py` prints a formatted credential table at startup.

Route ordering places `/api/complaints/alerts` and `/api/complaints/trends` before `/<int:complaint_id>` routes, avoiding the Flask routing conflict that would have shadowed them.

### Auth model and session security

Session cookies use `SESSION_COOKIE_SAMESITE = "Lax"` and the `SECRET_KEY` is pulled from the environment with a fallback of `"dev-secret"` for local development — appropriate for a demo context. The `manager_required` decorator checks login first, then role, which is the correct layering. Role is read from the server-side session only; the frontend cannot escalate privileges by sending a crafted role.

### Customer data isolation

`list_complaints` applies the ownership filter inside the route handler after reading `current_role()` and `current_user_id()` from the session. This means an unauthenticated caller sees all complaints (preserving the public dashboard), a logged-in customer sees only their own, and a manager sees everything. The `detail` endpoint independently re-checks ownership with a 403 on mismatch, so customers cannot bypass the list filter by guessing a complaint ID.

### New routes registered and ordered correctly

All required routes are present (confirmed by `app.url_map.iter_rules()`):

- `/auth/login`, `/auth/logout`, `/auth/me`
- `/api/complaints/alerts`, `/api/complaints/trends` (before `/<int:complaint_id>`)
- `/api/complaints/<id>/detail`, `/respond`, `/note`, `/status`, `/similar`, `/priority-explanation`, `/responses`
- `/customer`, `/management`

The static routes (`/`, `/health`, `/static/<path:filename>`) are unchanged.

### Database schema additions

`User`, `ComplaintResponse`, `InternalNote` tables confirmed present. `Complaint` has the four new columns: `status`, `assigned_to`, `resolution_notes`, `resolved_at` — all nullable, so existing seed rows are unaffected. Relationships are correctly defined: `Complaint.responses` and `Complaint.notes` use `lazy="dynamic"` allowing `.all()` and filtered queries in the route handlers.

### Seed integrity

All 6 demo users seeded with correct roles (2 `manager`, 4 `customer`) and werkzeug-hashed passwords. `seed_users()` is idempotent (count check before inserting). Complaints for alice, bob, and carol are linked to their user IDs after seeding.

### Frontend portals

Customer portal (`customer.html`): dark blue/teal theme (`--bg:#060d14`, `--accent:#0ea5e9`) with 3 tabs (My Complaints, Submit Complaint, Track Complaint), security disclaimer present at bottom of Track tab ("This is a simulated customer portal for demonstration purposes...").
